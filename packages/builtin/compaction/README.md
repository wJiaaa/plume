# 上下文压缩

长会话快装不下时，先剪掉过大的工具结果，还不够就把较早的那段换成一份结构化的摘要，最近的原样留着。随应用发，不能停用。

## 它做了什么

- **每次发请求**（`model.context` 的里层）：一条工具结果第一次发出去前超过约 32k 字的剪成头尾，中间换成一个标记和 `artifact://` 地址（原文经 plume.tools 的服务 `resources` 存着，模型要看就 read）。同一条每次剪出同一份，发出去的前缀不变，缓存接得上。
- **什么时候压**（`context.compact` 的里层）：量一下这次要发的请求有多满（能用服务商记的用量就用，不然按字数估），到窗口的 90%（小窗口还要给摘要留位置；有价格分档的模型按不低于 128k 的最低一条分档线算）就压；服务商说超长、人敲 `/compact` 时不管多满都压。一轮干净收尾、缓存还热时也看一眼，这时只在能分叉时压。
- **先剪枝**：没搜到、空目录这类结果（工具标了 `uneventful`）清空；早就被后面的读、改盖过的结果，和超过约 8k 字、模型已经看过的结果剪成头尾。剪完落到触发线以下一成就不摘要，只把剪过的结果交给宿主记下（`pruneOnly`）。
- **留多少**：从后往前留原文，最多约窗口的 12%，至少 4 条；不从工具结果切开，不切进上一次换上的头里。对话太短（不超过 6 条）、切不出可收起的一段时不压。压完放不下就从留下的尾部最老的往后删，直到放得下。
- **摘要**：缓存还热（同一个模型、离上一次主请求不到这家服务商的缓存时长，默认 4.5 分钟）时从主请求分叉，接着下一次要发的那份历史问，吃到缓存；分叉放不下、前缀对不上、调了工具、出错时退回单独的摘要请求（同模型、不带工具、不思考），太长的分段写、最多四遍，一段里放不下的长结果和长参数先截短。都没拿到就本地机械整理一份；连这也放不下就按条丢掉最老的几轮。格式固定成目标、约束、进度、决定、下一步、关键上下文几节；第二次起是更新上一份，不是重写。花销记在会话名下。
- **摘要头**：摘要前面带上最新那条请求的原话和更早的请求（`<task-context>`，含批准的计划），读过、改过的文件，以及一句「原文能用 `recall` 找回」；宿主原样存下，以后每次照发。
- **`recall` 工具**：在这个会话存下的全部原文里按词搜（每个词都要出现、不分大小写），最新的在前，长消息在匹配处开窗引出，`offset` 往回翻页；搜不到自己的调用和结果。
- **`/compact [希望保留的内容]`**：现在就压，说明进摘要的指令；对话在跑时不压。
- 会话里的消息一条不动，界面上整段对话照样看得到；摘要、边界、剪过的结果由宿主记下，重开应用也照样发。转录里画一行压缩：自动的进行中、等重试、本地整理、失败、被中断留在行里，压完是一条分隔线；人敲的 `/compact` 是一只气泡加一行进度和结果。

## 换成自己的

它挂在钩子 `context.compact` 的里层（order 1000）。在外层加一层、不调 `next`，返回 `{ keep, summary, head, via?, views? }`（从历史的第几条起原样留着、前面换成什么）、`{ pruneOnly: true, views }` 或 `undefined`（不压），就整个换成你的压法；摘要要调模型的话用 `ctx.model.complete({ sessionId, messages, ... })`，要从主请求分叉加 `fork: true`。字段见 skill `plume-plugin` 的 `references/logic.md`。

## 已知的边界

- `artifact://` 存的原文只在内存里（每个会话 30 份）：重开应用以后剪过的结果照样剪着发，地址却读不回原文了，要看全文得重新读文件或重跑命令。
- 一轮收尾以后为了分叉，宿主会再经一遍 `model.context` 组出下一轮开头那份请求，`model.context` 的层在一轮里可能多走一次。
